## B. Единый протокол предварительного сравнения

Первый запуск можно выполнить на неизменённом текущем processed-корпусе, явно обозначив его как предварительный эксперимент по меткам источников. Не называй это финальным качеством распознавания стиля.

Создай один manifest разбиения train/validation/test, ориентир 70/15/15 по исходным документам с сохранением всех пяти классов. Доли фрагментов могут отличаться; покажи реальные количества. Используй seed=42, не подбирай seed по результатам модели.

- Базовая группа — канонический source_url без #chunk=, с осторожной нормализацией URL. Не объединяй все строки без URL в одну группу: выдай ошибку или создай документированный fallback ID.
- Объедини в группы точные нормализованные дубликаты, включая совпадения между URL. Конфликтующие метки вынеси в отчёт для проверки.
- Если успеваешь, добавь кандидатный поиск близких дубликатов с фиксированным правилом, основанным на исходном тексте. Порог обоснуй примерами; не подбирай его по F1 и не удаляй все похожие правовые шаблоны автоматически. Если не успеваешь, зафиксируй непроверенные близкие дубликаты как ограничение.
- Все фрагменты одной группы должны находиться в одной части. Сохрани идентификатор каждого фрагмента и fingerprint версии текста; manifest должен валидироваться по хешу корпуса.
- Проверь отсутствие пересечений doc_id / duplicate_group_id между частями и наличие каждого класса. Не используй leave-one-domain-out, в котором из train исчезает тестовый класс.

Выбери гиперпараметры до просмотра test. Минимально:

1. DummyClassifier как контроль.
2. Word TF-IDF (1,2) + LogisticRegression, C=1, class_weight='balanced', фиксированные параметры.
3. Тот же Word TF-IDF + LinearSVC, C=1, class_weight='balanced'.

TF-IDF обучается только на train внутри Pipeline. Не добавляй в признаки URL, site, метку, doc_id, служебные поля. При нехватке времени не устраивай поиск гиперпараметров. Если настраиваешь параметры, используй только validation; после фиксации конфигураций выполни test один раз для каждого заранее выбранного варианта.

Основная оценка — на уровне исходных документов: агрегируй предсказания фрагментов по заранее фиксированному правилу, например большинство голосов с детерминированным разрешением ничьей. Дополнительно покажи метрики по фрагментам. Разные URL в одной группе дубликатов должны оставаться в одной части; отметь, если метрики всё ещё взвешивают повторные документы.

Для всех моделей используй labels=[0,1,2,3,4]. Сохрани Macro-F1, weighted-F1, accuracy, precision/recall/F1/support по каждому классу, confusion matrix, предсказания с ID и временем запуска. Сохрани модели и параметры. Проверь, что загруженная модель выдаёт те же предсказания на небольшой фиксированной выборке.

## C. Исправления предобработки — следующая версия корпуса

Не смешивай исправление корпуса с интерпретацией старых метрик. Делай отдельный v2 с журналом изменений.

## D. Следующий этап обучения после первого отчёта

Подготовь возможность обучения трансформера на тех же manifest. Используй точное имя checkpoint и закреплённую revision; сохраняй tokenizer, config, label mapping, все параметры, seed и хеш корпуса вместе с моделью. Не называй Kaz-RoBERTa другой моделью только из-за имени скрипта.
